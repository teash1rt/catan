# 卡坦 Blender 建模

## 开始前

读取 [资产计划与契约](../../../docs/modular-asset-plan.md) 和 [审美规范](references/art-direction.md)；导出时读取 [资产工作流](../../../docs/blender-asset-workflow.md)。用户本次明确要求优先于默认风格和流程。

默认追求明亮、有色彩层次的手绘游戏感，而非微缩写实。先确认棋盘尺度的剪影和配色，再添加克制的近景细节；不得把面数、叶片数量或写实程度当作质量指标。

确认目标资产、当前实施阶段、已有 `.blend`、已确定的尺寸/挂点及验收范围。尚无契约数值时先完成计划第一阶段并记录基准，不在每个模型上各自猜测。只推进本次请求涉及的资产。

发现当前可调用的 Blender MCP 与 Computer Use 能力，按实际工具文档使用，不虚构工具名称或连接成功。先查看已有场景，避免覆盖无关对象或未保存工作；源文件和输出路径采用项目约定，修改前保留可恢复版本。

## 工具职责

- **Blender MCP**：优先用于场景读取、建模、材质修改、挂点设置及导出；可通过其实际支持的能力执行 Blender Python。
- **Computer Use**：操作 Blender 界面、切换视角和显示模式、截取并查看真实画面。MCP 返回成功、模型统计和脚本日志都不能替代这一步。
- MCP 不可用时明确报告缺失能力；只有其他方式在现有授权内可用时才采用，并说明替代方式，不自动安装或配置工具。
- Computer Use 不可用时，可继续已授权的建模或技术检查，但视觉评审标为未完成；不得以后台渲染或 MCP 截图冒充 Computer Use 评审。

## 建模—评审循环

1. **建立基线**：使用 Blender MCP 制作或调整资产；优先轮廓、比例、结构，再处理材质与局部细节。保存版本，保持既有尺寸、挂点和材质契约。
2. **实际查看**：通过 Computer Use 在 Blender 中检查棋盘视角、近景和侧面；使用中性光照查看真实材质与阴影。首次记录镜头、缩放、光照和显示模式，后续同条件比较。
3. **记录缺陷**：依照审美规范逐项判断通过/不通过/未检查，记录截图、具体位置、可见问题及拟修改动作。每轮优先解决最影响轮廓、可读性或质感的问题，不用总分替代证据。
4. **修正复核**：通过 Blender MCP 修正，再通过 Computer Use 用相同视角复查，记录问题是否改善，并检查是否引入遮挡、穿插或契约破坏。
5. **导出复核**：视觉检查通过后导出 GLB；检查尺寸、法线、材质、挂点、意外节点和资源预算。在独立检查场景重新导入 GLB，并通过 Computer Use 检查导出效果；桌面端可用时再验证游戏视角。未检查的平台如实标记。

先做一次基线检查，默认最多追加 **3 轮修正—评审**，导出引起的修正也计入预算。全部适用项通过即可结束；连续两轮对已列主要缺陷无可观察改善，或三轮后仍不通过，停止迭代并交付当前最佳可恢复版本、截图与剩余问题。额外轮次仅在用户明确要求时继续。

缺少必要工具或无法查看产物时停止依赖该能力的步骤，报告未完成项；不重新解释“通过”来迁就工具缺失。

## 交付证据

- `.blend` 与已导出的 `.glb` 路径；未导出则注明原因。
- 按资产工作流交付固定路径的最新 `.blend/.glb`，不设版本目录，不默认交付预览、切图或评审文件；更新 [模型资产清单](../../../docs/asset-inventory.md)。草稿与恢复副本放项目外，验证后再替换正式产物。
- 实际使用的建模/评审工具、修正轮数、评审视角，以及截图路径或工具提供的图像引用。
- 每轮简表：`问题与位置 | 修改 | 对比证据 | 通过/不通过/未检查`；另列技术校验和桌面端复核结果。
- 评审截图、渲染与记录放临时目录或保留为会话证据；区分渲染预览图和 Computer Use 截图，不得互相冒充。清理归档不等于重新通过视觉评审。
- 分别报告 **指令/格式校验、视觉评审、GLB 技术校验、桌面端复核** 的状态。只有本阶段要求的验收均有证据，才在资产计划中勾选完成；用户的最终审美判断优先。
